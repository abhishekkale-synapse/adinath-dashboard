Design Proposal

Per-user-input data capture for adaptive scoring

How the app captures each user input, computes an adaptive score, and feeds the UI recommendation layer -- end to end.

1 · Context

The app adapts its UI based on how a user interacts with it. Adaptation is driven by a score -- UAES -- that reflects the quality of a user's engagement in real time.

To compute UAES, a reliable stream of user input signals is needed. Three input types are in scope: Lexi chat, touch, and later eye tracking. Each input must be captured, tagged with context, scored, and made available to the UI recommendation layer.

The essential finding. Between July 31 and today, per-user-input capture is partial at best. Text is not landing. Classification does not exist as a stored field. Flow state is not stored. UAES itself is computed in Python but never persisted. Without capture, no score is possible.

2 · Why per-input capture matters

Adaptation cannot happen without a per-input signal. Three layered questions explain the rationale.

Question
Why capture data per user input rather than per session?
Definition
Per-input capture means every discrete user action -- a chat message, a tap, a gaze event -- produces its own row of data.
Answer
Because the UI recommendation adjusts in real time. Session-level capture is a summary -- useful for reporting, useless for live adaptation. Per-input capture is the input signal to the scoring engine.

What per-input capture enables

  • Live UAES computation. The engine reads the input, tags it, scores it, returns a value the UI can act on.
  • Full audit trail. Every score is traceable back to the exact input that produced it.
  • Cross-source consistency. The same scoring path applies to Lexi chat, touch, and eye tracking -- one engine, one output shape.
  • Recommender simplicity. The recommender queries one table for the current UAES and running SAES, no unions, no joins across signal sources.

3 · What needs to be captured

Every user input needs four pieces of information. Each has a different status today and a different owner.

Raw input
Not landing · since July 31

The user's actual input -- text for Lexi, action name for touch, gaze coordinates for eye tracking.

Owner: Lexi capture pipeline (for text). Frontend event pipeline (for touch, eye).

Kind and state (level 2 and level 3)
Not stored anywhere

Kind (level 2) -- which of the five kinds the user's input is: Condition, Need, Adjustment, Ambiguous, or Unrelated. State (level 3) -- how sure Lexi is at each round: Known, Somewhat known, Unsure, or Unknown.

Owner: Lexi classification and flow engine. Needs to expose these as stored fields when capture is rebuilt.

Page context
Available via frontend

What page the user was on when the input happened -- pageName and pagePath. Same shape intervention_events already uses.

Owner: Frontend. Small addition to the write payload.

UAES score
Computed but not persisted

The score itself, 0 to 5, plus the running maximum (SAES) for audit trail.

Owner: Scoring engine. Needs a table to write into.

The pattern this reveals. Only one of the four pieces requires a new table on the scoring side. Two of the four (raw input, classification and flow state) depend on the Lexi capture pipeline being restarted with additional fields. One (page context) is a small frontend addition. This is not one design problem -- it is three parallel workstreams that meet at the scoring table.

4 · How each piece works

The design splits by system boundary. Each system owns its piece; the pieces meet at the scoring table.

Lexi capture
Owner: Lexi backend
Restart raw text capture, add kind, state and round tracking as stored fields

When the Lexi backend receives a user message, it needs to save five things back to messages: the raw content (as before July 31), the kind (level 2 -- one of Condition, Need, Adjustment, Ambiguous, Unrelated), the state at each round (level 3 -- Known, Somewhat known, Unsure, Unknown), the round number, and the resolution (resolved or handed over).

  • Raw content -- as previously stored, decoupled from the deprecated embedding.
  • Kind -- new field on the message row, populated by the classifier at write time. One of the five level 2 kinds.
  • State -- new field on the message row, populated by the flow engine at each round. One of the four level 3 states.
  • Round number -- 1, 2, or 3. Some inputs resolve in round 1 (Known state); some need up to three (Unsure state).
  • Resolution -- 'resolved' if Lexi could act, 'handed over' if unresolved after all rounds.
Frontend
Owner: Mobile app
Send page context with each input payload

When a user sends an input from the app, the write payload includes the current page name and path. Same pattern intervention_events.trigger_context already uses.

  • {pageName: "the settings page", pagePath: "/settings"} attached to every input write.
  • Removes the need to reconstruct page context by joining across tables -- which is currently not possible because conversations.session_id and user_actions.session_id are two different namespaces.
Scoring engine
Owner: Backend Python + new table
Compute UAES per input, write the score to a new table

One new table in the scoring schema -- scoring.input_events. Every user input, from any source, produces exactly one row here after the scoring engine has computed UAES for it.

Design principle for the scoring side. Raw text, classification, and flow state stay where the Lexi system produces them. The scoring table stores only what it computes plus the reference back to the source row. Denormalisation is minimal -- just the audit fields (session, source_type, page context, timestamps) needed for the recommender to work without a join.

5 · End-to-end flow

How the three systems work together for a single Lexi text input.

Data flow across systems
Design rule. Every user input, regardless of source, passes through the scoring engine and produces exactly one row in scoring.input_events. The recommender reads only from this table. Sources feed in; scoring writes out; recommender consumes.

Touch and eye tracking flow the same way -- the source system captures the input, the scoring engine computes UAES for it, one row lands in scoring.input_events with source_type = 'touch' or 'eye'.

6 · Who owns what

Three systems, three ownership boundaries. Each has one clear job.

Responsibility across systems

The three do not depend on each other for delivery -- they can proceed in parallel. When all three land, the recommender has everything it needs from one table read.

7 · Alternatives considered and rejected

Six approaches were considered before landing on the design above. Each is rejected for a specific reason.

Extend messages with UAES columns
1,945 rows today, ~95% are button clicks with no scoring metadata. Adding classification / uaes columns means ~95% of rows have all-null values. Sparse and wasteful.
Stuff scoring into messages.metadata jsonb
No type safety on scoring fields. No clean indexes on classification or UAES. The metadata column becomes a dumping ground; queries slow and become error-prone over time.
Extend conversations.context
Session-level, not input-level -- wrong granularity for per-input scoring. Also empty on every current row, meaning no owner has defined what it is for.
Store scoring in user_actions.metadata
user_actions is a frontend event stream. Scoring is a computed output. Mixing them muddies the system boundary between raw signal capture and computed IP.
Adopt ClickHouse for scoring storage
ClickHouse pays off around tens of millions of rows per year. Current volume -- 12,040 user_actions in one month -- sits comfortably in Postgres. Deferred. Revisit threshold: 50 million rows per year.
Store any single field as free text without an enum
Kind, state, entry point all have a fixed vocabulary now (level 1: E0–E7, level 2: five kinds, level 3: four states). Storing them as free text loses the type safety and makes filtering error-prone. Enum types keep the data clean and match the language established in the level 1/2/3 diagram.
